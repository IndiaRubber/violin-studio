# Architecture

The React shell in `src/App.tsx` owns the three screens and the microphone session. `src/Staff.tsx` renders exercise note data as SVG using VexFlow; it uses an actual treble clef and VexFlow's ledger lines. Each note is a whole note in its own strict 4/4 measure, with a time signature, metronome mark, and final barline.

`src/audio.ts` owns `getUserMedia`, Web Audio nodes, polling, and cleanup. It never connects the microphone to speakers. `src/pitch.ts` wraps Pitchy's McLeod pitch estimate, rejects low RMS/clarity/out of range readings, and median smooths accepted frequencies. `src/music.ts` converts frequencies to named octaves and signed cents from the actual target. `src/exercise.ts` tracks sustained matches, ordered progression, and release between targets. `src/config.ts` centralizes thresholds. `src/tempo.ts` holds pure timing functions (whole note = 240 / BPM s). `src/sustain.ts` is the two-phase sustained-note engine (find, then hold for the written duration) and shares the `PracticeEvaluation` result shape. `src/practice-session.ts` builds the exercise notes for the selected string focus, routes readings to the sustained engine or the unchanged quick `ExerciseEngine`, and enforces reference-tone suppression. `src/tone.ts` is an output-only Web Audio reference tone player with its own lazily created AudioContext; it never connects to the microphone graph. `src/Practice.tsx` owns the practice screen and its microphone session (as `Tuner.tsx` does for the tuner) and throttles React updates to about 10 per second. This separation allows swapping pitch detection, capture, notation, or exercises independently.

Pitchy's `forFloat32Array(4096)` and `findPitch(samples, sampleRate)` API was verified against its published documentation. The application pins dependencies and a lockfile. The detector's clarity is a signal quality heuristic, not a calibrated probability. Audio and UI are entirely client side.

The analysis window is 4096 samples (about 85–93 ms at common sample rates), polled every 50 ms. Analyser frames overlap. One isolated pitch jump is quarantined; two consistent observations establish a transition. Rejected frames produce no accepted pitch, and smoothing history expires after more than two consecutive rejected frames. The engine permits up to 110 ms between verified matching observations, but silence or a verified wrong pitch resets a hold. Advancing requires a fresh correct observation after 350 ms. A 180 ms continuous quiet period, or a confirmed pitch change, releases the next target. These settings are starting points for physical testing, not universal violin thresholds.

Sustained-note timing uses the same `performance.now()` timestamps as the audio poll, so engine tests drive it with a controllable clock. The hold measures the gap since the last verified good reading before accepting a new one, so a microphone interruption (no readings at all, such as a suspended AudioContext) longer than the grace period resets the hold even if the next frame is correct. Reference suppression discards all evidence for the current note and any release-in-progress, so the app's own tone cannot start, extend, or complete a note.
